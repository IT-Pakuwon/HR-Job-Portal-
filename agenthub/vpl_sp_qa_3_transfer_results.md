**Residual gap, downgraded from data-integrity to robustness:** the second concurrent caller now gets a raw Postgres `23505` error propagated through Laravel's `QueryException`/`PDOException`, not one of the procedure's own `RAISE EXCEPTION '<Indonesian business message>'` calls. A caller (app code or a human operator) can't distinguish this from any other unexpected DB error, and there's no automatic retry — the losing transfer simply fails and needs to be manually resubmitted. Recommend the procedure catch `unique_violation` (`EXCEPTION WHEN unique_violation THEN ...`) around each bootstrap `INSERT` and either retry the `INSERT`/`UPDATE` sequence once within the same call, or re-raise with a clear message telling the caller to resubmit — so this doesn't surface as a raw constraint-violation string to end users once this proc is wired into the report-ledger feature.

## SPT-07 detail — confirmed race condition

The `FOR UPDATE` lock taken on the transfer header (`tr_vpl_transfer h ... WHERE h.transfer_id = p_docid`) only locks **that one document's row**. It provides no serialization between two *different* transfer documents that happen to target the same `ms_vpl_product_bal` key (`year`/`cpnyid`/`product_id`/`expired_date`/`whs_id`) or the same `ms_vpl_product_detail` key (`cpnyid`/`product_id`/`expired_date`/`whs_id`). Both tables bootstrap missing rows via a plain `INSERT ... SELECT ... WHERE NOT EXISTS (...)` (proc lines ~1105-1222 for bal, ~1306-1368 for detail), and neither table has a unique constraint on its business key — confirmed directly: `pg_constraint`/`pg_indexes` show only the surrogate `id` primary key on both tables (same gap already flagged at the master-data level in `vpl_sp_qa_1_master.md` SPM-01).

Test method: two PHP processes connected directly via PDO, synchronized on a file-based barrier so both fire `CALL sp_process_vpl('VPT', ...)` within tens of microseconds of each other (verified via logged start timestamps), targeting two different transfer documents against the same brand-new product/warehouse/year key (never previously bootstrapped).

- **`ms_vpl_product_bal`**: reproduced on the first trial. Two concurrent calls (`VQAT0810T10`, `VQAT0810T11`, started 45µs apart) against a fresh `year=2027` key produced **4 rows instead of 2** — one duplicate pair for the source warehouse and one for the destination warehouse, each row holding only one call's ±5 qty movement instead of both calls sharing a single accumulated row. Both calls returned success with no error.
- **`ms_vpl_product_detail`**: attempted 3 separate trials (fresh product/warehouse pairs each time, ~20µs–120µs start offset) — none reproduced a duplicate row in this run. Given the identical `INSERT...WHERE NOT EXISTS` pattern and identical absence of a unique constraint, this is read as a narrower empirical race window in this environment on this attempt count, not evidence that the table is safe. Flagging as the same class of risk, unconfirmed by direct reproduction.

**Why this matters**: with duplicate `ms_vpl_product_bal` rows sharing the same non-unique key, every future `sp_process_vpl` call against that key will match *both* rows in its `UPDATE ... WHERE year = ... AND whs_id = ...` statements (Postgres updates all matching rows), silently doubling every subsequent period movement recorded against that key. Any report or `SUM()` query built on the assumption of one row per key will be wrong from the moment a duplicate is created — directly undermining the reason `sp_process_vpl` was adopted as the report-ledger write-point in the first place. Recommend adding a `UNIQUE (year, cpnyid, product_id, expired_date, whs_id)` constraint on `ms_vpl_product_bal` and `UNIQUE (cpnyid, product_id, expired_date, whs_id)` on `ms_vpl_product_detail`, or serializing the bootstrap step with an advisory lock keyed on the same business key, before this procedure sees concurrent production traffic.

## Observations (not gaps, informational)

- SPT-03's destination-conflict guard and the Submit-side source `v_qty <> 0` guard are both scoped by `refnbr = p_docid` — they detect re-submission / desync *within the same document*, not a general cross-document conflict on the same product/warehouse key. Worth knowing if this guard is ever assumed to catch cross-document issues; it doesn't.
- SPT-04 confirms rollback is transaction-wide per `CALL`, consistent with the VPR branch's behavior (`vpl_sp_qa_2_receive.md` SPR-03/SPR-07) — no partial commits observed even though the ledger INSERTs happen before the stock-sufficiency check in code order.
- SPT-01/02 confirm the dynamic `EXECUTE FORMAT('...period%1$sin...period%1$sout...', LPAD(v_month::TEXT,2,'0'))` substitution is correct across month boundaries (01, 06, 08, 12 all exercised) — no typo or off-by-one found in the format string or `LPAD` usage.
