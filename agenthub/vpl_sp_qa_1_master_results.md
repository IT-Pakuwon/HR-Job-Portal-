# QA Results: sp_process_vpl — Master Data Invariants

Executed 2026-08-10, branch `JP-backend`, against `public.sp_process_vpl` on connection `pgsql5` / database `db_das_test` (verified live via `select current_database()` before any writes). Companion to `vpl_sp_qa_1_master.md`.

**Pre-flight note**: `.env`'s `DB_PGSQL_DATABASE_5` was found pointed at `db_das` (not `db_das_test`) mid-session, then corrected back to `db_das_test` before any test ran. Confirmed via `git diff`/live query that all work below executed against `db_das_test` only.

| ID | Result | Expected | Notes |
|---|---|---|---|
| SPM-01 | GAP confirmed → **FIXED 2026-08-10** | Flag if no DB-level UNIQUE on the business keys | Confirmed via `information_schema`/`pg_indexes`: both `ms_vpl_product_bal` and `ms_vpl_product_detail` had **only** a `PRIMARY KEY` on `id`. No unique constraint existed on `(year, cpnyid, product_id, expired_date, whs_id)` or `(cpnyid, product_id, expired_date, whs_id)`, leaving the proc's `UPDATE ... IF NOT FOUND THEN INSERT` bootstrap pattern unprotected against concurrent duplicate inserts. **Fix deployed to `db_das_test`**: added `UNIQUE NULLS NOT DISTINCT` constraints on both tables (PG16 supports this; plain `UNIQUE` would not have deduped two NULL-`expired_date` rows, which SPM-03 proved are valid). DDL at `agenthub/sql/spm_fix_constraints_20260810.sql`. Verified empirically: a manual duplicate-key insert now raises `SQLSTATE[23505] duplicate key value violates unique constraint "uq_ms_vpl_product_bal_key"`. **Not yet promoted to production `db_das`** — pending user decision. |
| SPM-02 | GAP confirmed → **FIXED 2026-08-10** | Flag if inactive product/warehouse still accrues stock | Static proof + empirical run agreed: `ms_vpl_product`/`ms_vpl_warehouse` were never referenced anywhere in the 2590-line proc body — an inactive-status product/warehouse could still silently accrue ledger/balance rows via `CALL`. **Fix deployed to `db_das_test`**: added a guard in all 4 doctype branches (VPR, VPT ×2 warehouses, VPU, VPS), right after each line's field validation, that raises an exception if a matching product/warehouse master row exists with `status <> 'A'` (a wholly missing master is intentionally left unblocked — out of scope for this fix). **Note**: the first deployment of this fix was silently overwritten minutes later by a concurrent session redeploying its own version of the proc (this series is being run across multiple concurrent sessions against the same shared `db_das_test` — see `project_vpl_qa_plan` memory). Caught it via a post-deploy re-check, re-fetched the then-current live proc (which by that point also carried a legitimate concurrent SPS-06 fix from Part 5/Settlement), reapplied the SPM-02 guards on top of it, and redeployed — confirmed both fixes coexist live. Full final proc at `agenthub/sql/sp_process_vpl_20260810_spm_fixes.sql`. Verified empirically post-deploy (twice, after each deploy): inactive product → `Product QAFXB (company QATEST) berstatus tidak aktif`; inactive warehouse → `Warehouse QAFXWHC (company QATEST) berstatus tidak aktif`; normal active-master Submit on both VPR and VPT still succeeds (no regression). **Not yet promoted to production `db_das`** — pending user decision. **Anyone touching this proc going forward should assume other sessions may be doing the same and re-fetch live before any `CREATE OR REPLACE PROCEDURE`, not rely on a locally cached copy.** |
| SPM-03 | PASS | NULL `expired_date` keys correctly, no drop/merge | Empirically created product `QASPM03` with two receive lines on the same product/warehouse: line 1 `expired_date=NULL` (qty 7), line 2 `expired_date='2027-08-10'` (qty 3). After `CALL sp_process_vpl('VPR','QASPM03RCV','QATEST','Submit',...)`: 2 distinct `ms_vpl_product_bal` rows and 2 distinct `ms_vpl_product_detail` rows, correctly split (`qty=7` on the NULL-expiry row, `qty=3` on the dated row) — no merging into one row, no dropped row. `IS NOT DISTINCT FROM` handles NULL as a valid, distinct grouping key as designed. |
| SPM-04 | PASS (documented) | Document current VPT `p_cpny_id` calling convention | Code confirms VPT's header lookup (proc lines ~734–754) achieves the same protection as VPR's explicit guard: `SELECT ... FROM tr_vpl_transfer h WHERE h.transfer_id = p_docid AND h.cpnyid = p_cpny_id FOR UPDATE` followed by `IF NOT FOUND THEN RAISE EXCEPTION 'Dokumen transfer % dengan company % tidak ditemukan.'` — a wrong `p_cpny_id` fails closed with a dedicated message, just phrased as "not found" rather than VPR's "company mismatch" wording. **Calling convention finding**: `grep -r sp_process_vpl --include=*.php` returns zero matches anywhere in the app — no controller, job, or command calls this procedure today. It is invoked purely manually/ad hoc by a human who must supply `p_cpny_id` themselves (presumably read off the transfer document's own `cpnyid` column), with no code enforcing that convention. Not a functional bug — the WHERE-clause guard means a wrong value fails safely — but there is currently no automated calling convention to document beyond "read `cpnyid` off the target document before calling." |
